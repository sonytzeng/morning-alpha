### Closing durability and CLE historical-write risks

The updated `closing-verification-engine/index.ts` uses `finalizeClosingReceipt`
for both new and fingerprint-reused snapshots. It first validates the real
Closing snapshot receipt, rereads the report's exact opening identity, updates
the report projection with an `updated_at` compare-and-set, and verifies or
retries the lifecycle advance with the same opening/closing IDs. The prior
unconditional fingerprint early-return path has been replaced in TS.
The evidence fingerprint includes
report date, opening snapshot ID/version and sorted close quote
symbol/value/change/capture/source fields. It is stored in the Closing decision
snapshot's `generated_text`, alongside the Closing contract. The new-snapshot
path publishes then reads back the durable snapshot before exposing report
completion. Snapshot RPC, report projection and lifecycle advance are still
separate writes; a source-level retry finalizer is not a transaction proof.
Consequently, fault-after-report, fault-after-snapshot, lifecycle-advance failure,
concurrent retries and changed-source fingerprint behavior need real DB receipt
and idempotency tests. No successful durable retry or atomicity result is claimed;
in particular, the common reuse/finalization path must be checked after an
interrupted report update or state advance. Missing snapshot publication is currently
reported as an incomplete Closing contract, not completed execution.

In `continuous-learning-engine/index.ts`, `loadPredictionAndMarketWindow` reads
the preceding 120-day window (up to 2,000 predictions / 10,000 snapshots), not
only the current opening revision. The updated entrypoint first validates exact
opening publication, durable Closing receipt and lifecycle identity; this
preflight prevents an unverified current close from entering the window run.
`updateOutcomes` still evaluates intraday, close,
1D/3D/5D horizons before the
current-opening Learning contract is evaluated. Reviews/cases, patterns, model
evaluations and rule/shadow evaluation also use the window. A current-day
contract failure therefore does not prove that historical outcome writes were
absent or rolled back. The run metadata's `production_rule_mutation=false` is
not a no-write claim for those learning tables. Actual historical rows affected,
partial-failure rollback, rerun counts, truncation effects, frozen revision
isolation and RLS/RPC behavior are **not DB-verified**; their counts are unknown,
not zero. `tests/closingLearningContract.test.mjs` explicitly uses synthetic,
in-memory fixtures and does not settle those durability questions.

The subsequent TS update narrows writes with `canWriteLearningOutcome`: completed
and past-due existing outcomes are preserved, new rows use insert/ignore-duplicate
semantics, and permitted updates compare existing status/`updated_at`. Trusted
forecasts are deduplicated by date/window/scope/symbol, and exact frozen opening
CMS/source-ledger identity is validated. Durable Learning authority is the
succeeded `learning_runs` row and its `metadata.learning_contract`, not a report
JSON completion alias. Lifecycle retries retain the same run/opening evidence.
These are implemented guards, not proof of zero historical writes or concurrency
correctness under PostgreSQL/RLS. Real row counts, failure boundaries, retry

## Permanent Product Contract — requirements for every future PR

This is the Consolidation V1 product contract, not a declaration that its
runtime gates are already green. Each candidate must attach its exact source
hashes and current-run evidence. A documented requirement or component assertion
does not constitute CI registration or a DB/browser result.

1. **Single Market Publication Path.** Raw input is normalized into canonical
   evidence; the market document is independently audited before one committed
   publication revision is made visible. A latest QA row, HTTP 200, report alias,
   semantic label or source counter alone cannot publish a report. Website,
   payload and LINE must resolve that same committed identity, not independently
   select the newest draft. The frozen opening identity cannot change when an
   intraday/current revision is published.
2. **Recommendation Isolation.** Company evidence, stock research, recommendation
   admission and paid depth are distinct from market evidence and market
   publication. Unsupported stock claims are retained privately and suppressed
   publicly; removing them is not permission to promote coverage to 100 or relax
   market/editorial/semantic validation. Market READY plus recommendation BLOCKED
   may publish an independently complete market report. An empty candidate list
   is not a completed-universe proof and must not become NO_QUALIFIED_OPPORTUNITY.
3. **Single Subscriber Projection.** Subscriber-facing state uses
   `getSubscriberReportProjection` from `src/lib/subscriberReportContract.ts`.
