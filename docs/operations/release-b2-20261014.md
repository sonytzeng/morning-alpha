# Morning Alpha B2 批次 LINE 失去回應恢復發布清單

本批只修外送請求的不可變性、失去回應重試及已接受409的恢復。V659文字、推薦V1來源、Token、Recipient及既有60秒重試／8次上限不變。不人工發送LINE。

## 唯一候選 SQL

`20261014002215_line_transport_immutable_request_candidate_v1.sql` 由Supabase CLI建立，尚未在Production執行。

新增私有requests／members兩表、FORCE RLS、不可變payload／recipient／retry-key與server-only權限。兩個新RPC `claim_line_transport_request_v1`、`complete_line_transport_request_v1` 僅service_role EXECUTE，固定search_path。原claim／mark函式及既有RLS／Auth不改。

另新增一個bound-outbox保護Trigger，禁止舊Sender或其他路徑以不同Key改寫／重試已綁定批次。它是本次SQL明確範圍，不能省略或移除以通過回滾。Migration只DDL，不回填舊已嘗試請求；其不確定結果須人工判斷。

## 唯一 Function

`line-daily-push`：以transactional request RPC租用完整固定批次，使用保存的原始body與Retry Key，不重新分批或以新版Renderer覆寫重試內容。200或409且有有效accepted-request-id才記為平台已接受；缺少409證據保持待重試，並非直接成功。每次HTTP有15秒上限。

[LINE官方重試契約](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)要求同Key重試內容與收件者相同；接受狀態不保證每名會員實際讀到或收到。完成紀錄、Outbox及成功log在同一fenced交易，避免接受後資料寫入中斷造成誤判。

## 驗證

真SQL＋實際Sender＋明示記憶體Provider協定控制：實際等原60秒、lost-ack→同body/key→409正確恢復、未知409／429重試、400拒絕、payload改寫拒絕、並行完整批次互斥、stale completion拒絕。原函式、Policy及ACL不變。所有外部LINE請求0；此結果不是LINE實際外送測試。

精確路徑／前後雜湊在 `staged-b2-transition-20261014.json`。部署需另核准唯一SQL、Sender SHA與依賴，保留現有custom Auth設定。

## 安全回滾

停止新版Caller並回復已保存V70 Sender原來源；只撤銷新兩RPC的server EXECUTE，保留新增私有表、Trigger及所有log／queue歷史。Fresh DB已實際驗證此回復。

重要限制：已綁定但平台是否接受仍不明的請求，舊Sender必須被Trigger拒絕，不能換舊算法Key補發。不得DROP新Trigger或刪除批次表。要恢復這些不確定批次，需要核對原Key／body／接受證據後由新版機制處理；不是盲目重送。沒有此保護就不能安全回滾。

新批次沿用正式is_active與訂閱者身分對應；重試時若固定組內任一會員已退出／身分改變，整組停於REVIEW_REQUIRED。保留原body/key與不確定歷史，不拆組、不標假SENT。重新啟用訂閱也不自動重送此組。Fresh DB已用實際60秒截止驗證。
